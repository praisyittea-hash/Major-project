# Module 6: communication

Socket.io `/chat` is authenticated separately from anonymous, payload-free availability sockets. Current JWT role, tenant/client relationship and CRM entitlement are checked for each action. Connections expire with the JWT. Events: `chat:join`, `chat:send`, `chat:message`, `chat:typing`, `chat:read`. Errors use acknowledgement `{ok:false,message}`. Messages persist before emission, carry server identity/timestamps and use a unique sender/message identifier for safe retries. Typing is temporary; read timestamps persist. History: GET `/api/chat/:clientId/messages?before=<ObjectId>`, 50-message cursor pages scoped to the authenticated conversation.

NotificationService uses a transactional DomainEvent outbox and uniquely keyed NotificationJob records. Booking confirmation and signed payment capture/failure publish inside their database transactions. A worker queues reminders during the 24 hours before confirmed sessions and follow-ups only after ended sessions are marked completed. GET `/api/notifications` is therapist-scoped; GET `/api/portal/notifications` is client-scoped. POST `/api/scheduling/sessions/:id/complete` allows the owning therapist to mark an ended confirmed session completed.

Each event queues WhatsApp and email jobs through isolated provider interfaces. **WhatsApp is always a persisted stub; no WhatsApp message is sent.** Optional Nodemailer email requires EMAIL_ENABLED and SMTP settings. `sent` means accepted by SMTP, not recipient inbox delivery. Disabled email stays disabled; enabling SMTP affects newly dispatched events. Provider failures retry with backoff and processing leases; SMTP delivery is at least once, so a crash after provider acceptance can cause a duplicate. Stable Message-ID helps providers deduplicate. Notification text contains a generic update and directs clients to their secure portal; clinical notes are never included.

Existing waitlist stub behavior is retained. HTTP APIs expose no delivery-provider credentials. Configuration: NOTIFICATION_POLL_MS, EMAIL_ENABLED, SMTP_HOST/PORT/SECURE/USER/PASSWORD/FROM; frontend VITE_SOCKET_URL optionally points to the API origin for split deployments.

Tests use actual WebSocket connections for two-way chat, tenant rejection, persistence after reconnect, retry deduplication, typing and read receipts. Outbox rollback and idempotency, actual booking/signed payment API events, the 24-hour boundary, and cancellation exclusions are tested with an isolated MongoDB replica set. Nodemailer is tested against a real local SMTP fixture; no external email or live WhatsApp delivery is claimed. The full regression suite, frontend build, lint and formatting pass before each commit.
